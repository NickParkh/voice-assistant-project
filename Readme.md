# Шаг 1. Анализ предметной области

# 1.1. Описание системы

Система представляет собой голосовой ассистент для персонального компьютера. Пользователь произносит команду (например, «открой браузер» или «поставь будильник на 7 утра»), система распознаёт речь, понимает намерение, выполняет действие в операционной системе или приложениях и отвечает голосом. Система нужна для безэкранного управления ПК, обеспечения доступности (для людей с ограниченными возможностями) и ускорения рутинных операций.

# 1.2. Акторы

Пользователи:
    -   Владелец ПК (подает голосовые команды).
    -   Разработчик (встраивает голосовой ввод в свои приложения через API).
    -   Администратор (управляет навыками и правами доступа).
Внешние системы:
    -   Операционная система ПК (Windows).
    -   Облачный ASR/TTS-провайдер .
    -   Календарь/Почта (для выполнения команд).
    -   Файловая система.

    Примечание -  (ASR - Сервис Автом распознавание речи -> текст, NLU - сервис, вытащить из текста намерение(что сделать) , Skill-service - сервис "руки" набор программ навыков, берет команду из NLU и совершает опред действие. 4 TTS - "Рот" синтез речи )


# 1.3. Пользовательские сценарии
1. Как владелец ПК, я хочу произнести команду и получить выполненное действие, чтобы не пользоваться клавиатурой.
2. Как владелец ПК, я хочу, чтобы система понимала контекст («поставь будильник на 7» → речь о календаре), чтобы не уточнять детали.
3. Как владелец ПК, я хочу услышать голосовой ответ, чтобы работать без экрана.
4. Как владелец ПК, я хочу добавлять новые голосовые навыки (например, «включи музыку»), чтобы расширять возможности системы.
5. Как разработчик, я хочу отправлять аудио через API и получать текст + намерение, чтобы встроить голосовой ввод в своё приложение.
6. Как администратор, я хочу управлять правами навыков (доступ к файлам, сети), чтобы система не выполняла опасные команды.

**Отвергнутые варианты разбиения:**
1. **Объединить `asr-service` и `tts-service` в `speech-service`.** Отказались: ASR — потоковый ввод с низкой задержкой и пиками, TTS — пакетный синтез; разные модели и ресурсы.
2. **Объединить `nlu-service` и `dialog-orchestrator`.** Отказались: NLU — ML-модель с частыми обновлениями, оркестратор — бизнес-логика диалога; при обновлении модели NLU не должны ломаться сценарии диалога.
3. **Отдельный `os-integration-service`.** Отказались: интеграция с ОС — техническая деталь исполнения навыков, без собственных бизнес-сущностей.

 Примечание - (sync) Программа-клиент ждет ответа, чтобы продолжить работу. (async) - Отправитель не ждет ответа (Пример - "Диалог завершен", "Команда выполнена" и.т.д)

3.«Зависит от»
Список сервисов, без которых сервис не может работать.

ASR: — (fallback: облачный ASR) — ни от кого не зависит, работает сам. Но если упадет, использует облако как запасной вариант.

NLU: ни от кого не зависит. Ему просто дают текст, он его разбирает.

Skill: ОС-интегратор (sync), dialog — зависит от операционной системы (чтобы открыть браузер) и от Оркестратора (который дает ему команду).

TTS: — (fallback: облачный TTS) — работает сам, но имеет резерв в облаке.

Оркестратор: asr, nlu, skill, tts (sync) — зависит от всех четырех сервисов, потому что он дирижер и вызывает их по очереди.

4. НФТ (Нефункциональные требования)
Это технические характеристики: насколько быстро, надежно и под какой нагрузкой работает сервис.

ASR: потоковый, p95 < 300 мс, 100 сессий — должен работать в реальном времени (стриминг), отвечать за 300 миллисекунд и держать 100 одновременных микрофонов.

NLU: p95 < 50 мс, 500 RPS — должен быть очень быстрым (50 мс) и выдерживать 500 запросов в секунду.

Skill: p95 < 200 мс, критичный — должен отвечать за 200 мс, сбой недопустим (критичный).

TTS: p95 < 400 мс, 100 RPS — генерация голоса занимает до 400 мс, выдерживает 100 запросов в секунду.

Оркестратор: p99 < 800 мс end-to-end — весь путь (от звука до ответа) должен занимать не более 800 мс.

5.Обоснование границы 

-   ASR: «Тяжелые ML-модели, нужно отдельное масштабирование» (распознавание речи требует много видеопамяти, поэтому мы держим его отдельно).

-   NLU: «Легкий быстрый сервис, частые изменения» (модели понимания языка часто обновляются, и мы не хотим перезапускать всю систему).

-   Skill: «Безопасность: изоляция команд» (если навык сломается или его взломают, он не должен утащить за собой всю систему).

-   TTS: Тяжелые ML-модели TTS (генерация голоса тоже требует много ресурсов).

-   Оркестратор: «Отдельная логика диалога» (сценарии общения — это бизнес-логика, ее нельзя смешивать с техническими нейросетями).

# Разделение хранилищ данных (Database-per-service)
Согласно требованиям, каждый сервис имеет собственное изолированное хранилище и не обращается напрямую к таблицам других сервисов:

-   dialog-orchestrator:** владеет базой `db_orchestrator` (история диалогов, контекст сессий).
-   asr-service: владеет базой `db_asr` (транскрипты, сессии распознавания).
-   nlu-service: владеет базой `db_nlu` (модели намерений, слоты).
-   skill-service: владеет базой `db_skill` (реестр навыков, права доступа).
-   tts-service: владеет базой `db_tts` (профили голосов, история синтеза).

*Все базы развернуты в едином кластере (SQLite на ПК или PostgreSQL в облаке), но логически изолированы (разные схемы/файлы) и имеют разных пользователей с ограниченными правами.*


# Шаг 3. Выбор готового ПО

Система спроектирована как гибридная (Offline/Online). Это обеспечивает высокую доступность: ассистент работает локально без интернета (критически важно для пользователей с ограниченными возможностями здоровья), а при наличии сети или слабом ПК — автоматически переключается на облачные вычисления.

| Компонент | Кто использует | Обоснование выбора |
| :--- | :--- | :--- |
| **SQLite (офлайн) / PostgreSQL (онлайн)** | nlu, skill, dialog | **Офлайн:** Встраиваемая реляционная СУБД, не требует отдельного сервера, файл базы лежит в папке с программой. Идеально для хранения настроек и истории на локальном ПК.<br>**Онлайн:** PostgreSQL используется в облачной инфраструктуре для синхронизации профилей, навыков и истории между устройствами пользователя. |
| **Локальная ФС (офлайн) / MinIO (онлайн)** | asr, tts | **Офлайн:** Веса нейросетевых моделей и аудиофайлы хранятся в обычных папках на диске (например, `C:\ProgramData\VoiceAI\models`).<br>**Онлайн:** MinIO (S3) обеспечивает облачное резервное хранилище для скачивания обновлений, хранения аудиофайлов и обмена моделями между устройствами. |
| **ZeroMQ (офлайн) / Apache Kafka (онлайн)** | Все сервисы | **Офлайн:** Легковесный брокер сообщений, работающий в памяти ПК (через localhost). | **ONNX Runtime (офлайн) / Облачные API (онлайн)** | asr, nlu, tts | **Офлайн:** Оптимизированный движок для запуска нейросетей прямо на процессоре (CPU) или видеокарте (GPU) без сети.<br>**Онлайн (Fallback):** Если локальная модель не справилась (шум, акцент) или ПК слабый, запрос перенаправляется в облачные API (Yandex SpeechKit, Google Cloud) для тяжелых вычислений. |
| **gRPC по localhost (офлайн) / REST API (онлайн)** | Все сервисы | **Офлайн:** Используется для синхронного общения микросервисов на локальном ПК. Работает быстрее, чем REST, и потребляет меньше ресурсов.<br>**Онлайн:** REST API используется для интеграции с внешними клиентами и облачными сервисами через интернет. |
| **Локальные логи (офлайн) / Prometheus + Grafana (онлайн)** | Все сервисы | **Офлайн:** События и ошибки записываются в локальные JSON-файлы для анализа разработчиком.<br>**Онлайн:** Prometheus собирает метрики в облаке, а Grafana строит графики мониторинга состояния системы в реальном времени. |

# Шаг 4. Схема взаимодействий

Система работает по принципу **Online-First**: при наличии интернета запросы идут в облако (для максимальной точности), при его отсутствии — автоматически переключаются на локальные модели (Fallback).

# 4.1. Архитектурная схема
[Архитектурная схема](docs/architecture.png)

*Описание:* Шлюз (API Gateway) проверяет наличие сети. Если сеть есть — запрос идет в онлайн-конвейер (облачные API, Kafka, PostgreSQL). Если сети нет — в офлайн-конвейер (локальные модели, ZeroMQ, SQLite). Каждый микросервис имеет собственное изолированное хранилище данных.

# 4.2. Диаграмма последовательности (Успешный путь)
[Успешный путь](docs/sequence_success.png)

*Описание:* Пользователь произносит команду. Шлюз направляет запрос в оркестратор (онлайн-режим). Оркестратор последовательно вызывает ASR (распознавание через облако), NLU (понимание), Skill (выполнение в ОС) и TTS (синтез голоса). Пользователь получает голосовое подтверждение.

# 4.3. Диаграмма последовательности (Сбой сети и переход в офлайн)
[Сбой и офлайн](docs/sequence_failure.png)

*Описание:* Пользователь произносит команду, но шлюз обнаруживает отсутствие интернета. Запрос перенаправляется в офлайн-оркестратор. Те же микросервисы выполняют команду, но используют локальные модели и файловую систему. Система успешно выполняет действие без доступа к сети.

# Шаг 5. Контракты API

Для всех сервисов написаны OpenAPI-спецификации (папка `api/`). В них учтена гибридная логика (флаги `useCloud` и `isOnline`), единая модель ошибок (RFC 7807) и защита от дублей (`Idempotency-Key`).

# Единая модель ошибок
Все сервисы возвращают ошибки в едином формате (RFC 7807):
```json
{
  "type": "https://api.example.com/errors/low-confidence",
  "title": "Речь не распознана",
  "status": 422,
  "detail": "Уверенность модели 0.31 ниже порога 0.7"
}
